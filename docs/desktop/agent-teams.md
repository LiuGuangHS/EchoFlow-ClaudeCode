# Agent Teams 协作工作台

Agent Teams 是 EchoFlow Code 的多 Agent 协作工作台，将团队成员、共享任务、成员通信和任务依赖集中展示。它适合需要角色分工与持续协调的任务，例如调研、实现、测试和复核；你可以看到谁在执行、谁被前置任务阻塞，并打开成员运行记录检查原因。它不只是普通 SubAgent 列表。

## 什么时候用

- 任务能拆成相对独立的角色或阶段。
- 你需要持续看到谁在做什么、哪些任务被依赖卡住。
- 你希望在一个主会话里汇总多个成员的结果。

如果你已经知道只需改一个文件，直接在当前会话完成通常更快。

## 从会话打开工作台

先在会话中要求 Agent 创建或加入一个 Team。团队开始运行后，打开右上角的**活动面板**，选择对应的团队条目即可进入工作台。

工作台显示的是团队当前状态；团队结束后，已完成会话仍可从活动记录重新打开归档快照和成员运行记录。

可以先复制一个只读任务，熟悉协作过程：

```text
创建一个 Agent Team，为当前项目做一次只读的测试覆盖检查。
成员 A 查找核心功能和调用入口；成员 B 查找现有测试与运行命令。
两者完成后，成员 C 根据他们的结果列出最值得补的 3 个回归测试。
把工作放进共享任务列表，标明 C 依赖 A、B；主会话汇总文件路径与依据。
不要修改文件、安装依赖、调用外部服务或提交代码。没验证的地方明确写出。
```

这是给 Agent 的任务约束，不会创建额外的权限隔离；需要限制写入时，同时选择适合的[权限模式](./sessions.md)。

## 看懂工作台

- **概览**：显示团队阶段、已完成任务和总任务数。
- **成员**：显示每个成员的状态、当前任务和最近活动。点击成员可打开运行记录。
- **共享任务**：所有成员共用同一份任务列表。完成的前置任务会解除后续任务；被依赖卡住的任务会标成阻塞状态。
- **通信流**：展示成员之间的消息和任务通知，便于判断协调是否停住。
- **依赖泳道**：把任务按依赖关系排列。它用于观察，不会替你修改任务顺序。

## 停止、恢复与排查

- 停止主会话会停止该会话内仍在运行的工作；先在活动面板确认是否仍有后台成员。
- 成员卡住时，先打开成员运行记录，看最后一条工具调用、权限请求或错误。
- 已结束的团队可从对应会话的活动记录查看归档状态；归档用于阅读和恢复上下文，不会自动重新执行成员。
- 团队删除前，桌面端会保留可查看的最终工作台快照；不要把工作台当作源代码或聊天记录的唯一备份。

## 权限与数据边界

Team 成员仍受各自会话的 Provider、模型、工具和权限模式约束。工作台只展示协调状态和已允许的运行事件；它不会绕过权限模式，也不会把私密 Provider 凭据显示给其他成员。

对敏感仓库，先用隔离 Worktree，再创建团队。最终改动仍应在工作区中逐文件审阅。

## 怎样验收，什么时候不用

- 示例中的 A、B 应各有结果，C 在使用这些结果后再给建议；共享任务的状态不能代替证据。
- 主会话应给出可打开的文件路径、已有测试的依据，以及没有核实的部分。只读任务结束后，用 `git status` 和 `git diff` 确认没有意外写入。
- 做实现任务时，成员显示「完成」不等于测试通过；仍需逐文件审阅 Diff，并运行与目标对应的测试。
- 多成员会增加模型调用和协调开销；能在单会话完成的小改动不必建团队。若成员要改同一文件，先划清写入范围，不要把共享任务列表当成文件隔离。

## 常见区别

**Agent Teams 和普通子 Agent 有什么区别？** 子 Agent 适合派出一个边界清楚的子任务，再把结果交回主会话；Teams 适合需要共享任务、成员通信和依赖协调的持续协作。见[子 Agent 与任务拆分](./agents.md)。

**Agent Teams 和 Dynamic Workflow 怎么选？** 重点是观察和协调角色、任务及消息时用 Teams；重点是把步骤写成可执行脚本、安排并发或流水线并复用编排时，看 [Dynamic Workflow](./dynamic-workflow.md)。两者都不能替代最终测试和人工审阅。
