# Dynamic Workflow

Dynamic Workflow 是 EchoFlow Code 的多步骤 Agent 编排能力：Agent 将任务写成可执行脚本，在同一会话中安排并发检查或按顺序交接结果，并在活动面板展示阶段与成员进度。它适合有明确依赖、需要汇总或希望重复使用的协作流程；普通提问和小改动不必使用工作流。

## 适合的场景

- 同时检查前端、服务端、测试或文档。
- 多个独立调研结果需要汇总后再决定下一步。
- 一组任务必须按顺序传递结果。
- 希望把完成过的编排保存为可重复调用的命令。

简单修改、单个已知命令或一个 SubAgent 能完成的任务，不需要 Workflow。

## 如何开始

在会话中直接说明目标和约束。Agent 可以创建并运行工作流，也可以将已完成的编排保存为工作流命令。保存前先确认脚本只调用你愿意授权的工具和范围。

运行后，活动面板会显示阶段、成员和进度。打开成员可查看它的运行记录；打开工作流活动可查看阶段状态和最终结果。

先用一个只读流程验证编排，不急着保存命令：

```text
用 Dynamic Workflow 对当前项目做一次只读的变更风险检查。
先读取 git diff，确定本次改动范围；没有改动就停止并说明。
然后并行检查：A 查找受影响的调用方，B 查找相关测试和未覆盖的边界。
等 A、B 都结束后再汇总，只报告有文件路径与依据的风险，并给出最小验证命令。
不要改文件、安装依赖、调用外部服务、提交代码或保存为命令。
某阶段失败时保留已完成结果，说明失败原因，不要声称检查通过。
```

提示词描述的是目标与约束，不是额外的权限门禁；仍需按任务设置会话权限。

## 并发与流水线

- **并发**适合彼此没有前置依赖的检查，例如代码审查、安全审查和测试设计。
- **流水线**适合下一步必须使用上一步结果的工作，例如先定位调用点，再实现，再验证。
- 并发不会自动降低权限或成本；每个成员仍会消耗模型额度并受工具权限约束。

## 中断与恢复

- 中断会停止仍在运行的工作，不会自动撤销已经写入工作区的文件。
- 恢复前先审阅已经产生的 Diff、阶段结果和失败原因。
- 已完成的运行会在会话活动中保留历史，方便查看脚本、阶段和成员结果。
- 如果工作流需要重跑，优先从失败阶段或最小范围开始，避免重复执行已经验证通过的昂贵步骤。

## 安全与审阅

工作流不会绕过会话权限。涉及写文件、Git、网络或外部服务的成员仍会触发相应权限规则。不要把密钥、私人路径或未经验证的外部内容直接拼进工作流脚本。

对会写代码的工作流，结束后仍需检查 Diff、运行定向测试，并在需要时使用隔离 Worktree。

## 怎样验收，什么时候不用

- 示例应先确定改动范围，再执行两个独立检查，最后汇总。检查结果应引用文件或测试依据，而不是只有「已完成」。
- 一次运行没有报错，不代表代码正确。核对脚本、成员输出、最终 Diff 和定向测试结果；失败或未执行的检查要单独列出。
- 停止不等于回滚，恢复也不等于所有步骤都能安全重放。对写文件或调用外部服务的步骤，重跑前先确认是否已产生效果，避免重复修改或重复请求。
- 一个已知命令就能解决的任务直接运行即可；多 Agent 编排会增加模型调用，不能保证更快、更便宜或更可靠。

## 常见区别

**Dynamic Workflow 和 Agent Teams 有什么区别？** Workflow 的重点是可执行的步骤编排、并发和顺序交接；[Agent Teams](./agent-teams.md) 的重点是团队角色、共享任务、消息和依赖关系的可视化协调。

**它就是定时任务吗？** 不是。Workflow 描述任务怎样协作执行；[定时任务](./schedule.md)解决何时自动启动任务。保存为工作流命令也不等于已经设置定时触发，保存前仍需审阅授权范围。
